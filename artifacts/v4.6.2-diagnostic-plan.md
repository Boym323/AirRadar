# AirRadar V4.6.2 Operational Twin diagnostics

## Scope

This branch is based on current `main` (`5b1e972f`). It does not include the
truth reuse, pending evaluation, or trail behavior changes from draft PR #885.
The existing validation algorithm and production toggles remain unchanged.

## Collected metrics

When enabled, the existing authenticated `/api/system/runtime-performance`
endpoint returns aggregate Operational Twin forensics alongside completed
event-loop windows. Phase scopes cover truth input fingerprinting, truth-point
construction, truth-state diffing, pending traversal and evaluation, spatial
matching, ATC context computation and cache access, expiration, capacity
eviction, and cleanup. Each scope reports exact cumulative and per-minute call
counts and every-256th-call CPU/wall samples, estimated totals, CPU and wall
P50/P95/P99 when at least 20 samples exist, and sampled maxima. CPU/wall
estimates use the sampled per-call mean multiplied by the exact call count;
the sample count is reported separately. A window with no timed samples has no
CPU/wall estimate.

The report also includes snapshot invocation intervals, pending population
and pending-per-aircraft buckets, capture/expiration/truth invalidation and
resolution counts and per-minute rates, ATC cache hits/misses, and bounded
per-minute phase windows. Nested timings are inclusive; do not sum nested
phases. Truth invalidation counts mean the validator rebuilt a truth state
after source inputs changed. Truth-state diff timing covers building and
comparing the changed/correction point sets. These metrics contain no ICAO, callsign,
registration, position, trajectory, event title, provider payload, or cache
key.

The existing runtime sampler retains CPU, event-loop, GC, history persistence,
network metadata, Route Cache, and snapshot measurements. Event-loop windows
now include GC count and pause deltas. Runtime status exposes cgroup CPU quota
and cumulative throttling counters when the host provides them. T57 samples
align completed windows with hot-path and Twin phase windows and report
descriptive correlations only. Those correlations do not establish causation.
The offline report separates sampled synchronous CPU scopes above 1 s in
overlapping event-loop windows, strong correlations (at least 10 paired
windows and Pearson r >= 0.7), and high-lag windows without direct phase
evidence. Unsampled scopes remain possible explanations for the latter.
To prevent nested CPU double counting, the detailed Twin correlation adds only
the disjoint top-level phases pending traversal, expiry heap, capacity eviction,
and cleanup. Each invocation of those scopes and truth-state diff is checked
against a 1 s wall-duration threshold. Only a fixed per-phase count and maximum
are retained, so rare long operations can be found outside the regular
1-in-256 sample. Nested point matching and cache lookup remain sampled; an
enclosing traversal records any long synchronous block.

## Runtime controls and safety

Collection is off unless the operator sets
`AIRRADAR_OPERATIONAL_TWIN_FORENSICS_ENABLED=true` for the process. It requires
no ATC, watchdog, database, or other production configuration changes. The
report is available only through the authenticated runtime diagnostics route.
CPU and wall timing reservoirs are capped at 128 values each per phase;
per-minute windows retain at most 30 minutes. Long-operation detection retains
only fixed per-phase counts and maxima, never per-operation records. Logs are
not added. When disabled, phase scopes execute their existing operation directly and the report returns only
`enabled: false`.

## Overhead benchmark

Run `npm run benchmark:twin-forensics` to compare a direct 120-point
synchronous scan with diagnostics disabled, sampled diagnostics enabled, and
the all-call long-duration guard stress path. The isolated development-host
run used 300,000 invocations per round, five warmup rounds, eight measured
rounds, and sampling at 1/256 calls. Median wall times were **258.152 ms
uninstrumented**, **266.019 ms disabled**, **392.974 ms enabled**, and
**477.428 ms for the all-call guard stress case**. Process CPU medians were
**258.077 ms**, **265.600 ms**, **393.099 ms**, and **476.583 ms** respectively.
The enabled two-scope path added an estimated **450 ns CPU per invocation**;
guard checking on both scopes in the stress case added a further **278 ns**.
The fixed timing/counter cost is a large percentage of this sub-microsecond
synthetic operation, so the percentage must not be applied to the much longer
production traversal. Production all-call checks are limited to traversal and
low-frequency expiry, capacity, cleanup, and truth-diff scopes; nested hot
paths use 1/256 sampling. After forced GC, enabled diagnostics changed
**+67,400 heap bytes** and **+1,531,904 RSS bytes** in this run. This synthetic
single-process benchmark is not a production-load regression gate. The metrics
stores have explicit
caps: 128 CPU and wall latency values per phase, 30 phase windows, fixed
counter maps, and scalar maxima rather than event records.

## T57 reliability

New unavailable rows store an allowlisted failure category: HTTP timeout,
authentication failure, response validation failure, HTTP failure, or network
failure. Samples also record bounded poll lateness and label delayed polling.
The report compares late polls with completed server event-loop windows; that
correlation does not identify the cause by itself. Existing
T57 files contain no category field, so the four unavailable V4.5 samples
cannot be retrospectively classified from the supplied count.

## Controlled deployment plan

Keep diagnostics off by default. Before enabling collection, verify the
production build's exact commit through `/api/version`, confirm the authenticated
runtime-performance endpoint is reachable, and verify the runtime event-loop,
GC, process CPU, history, network, and Route Cache monitors are producing fresh
windows. Confirm an operator can read and preserve the existing `/var/www/airradar/.env`
securely, change only `AIRRADAR_OPERATIONAL_TWIN_FORENSICS_ENABLED`, preserve
its owner/mode, and restore the prior value. Do not print or copy the full
environment file into logs or artifacts.

For one controlled process window, set the diagnostic switch to `true`, restart
`airradar.service`, and verify health plus authenticated schema-version-4
telemetry reports `operationalTwinForensics.enabled: true`. Pin T57 to the exact
deployed commit; retain only its sanitized report. Monitor event-loop maxima,
CPU, heap/RSS, sample availability, and privacy output during collection. On
any health, overhead, or privacy regression, restore the saved flag value (or
set it to `false`), restart the service, verify health, and confirm the report
returns `enabled: false`. Do not extend collection if monitoring, exact commit
identity, or this configuration rollback cannot be verified first.

After the window, disable collection and evaluate T57. Attribute a long event
loop stall only to an overlapping sampled CPU phase or all-call long-wall
detector with matching timing. A correlation alone is not attribution. If no
scope evidence covers a stall, report `NOT ATTRIBUTED`. This diagnostic PR does
not alter Operational Twin algorithms, merge PR #885 or #878, change ATC
resolution, or deploy by itself.
