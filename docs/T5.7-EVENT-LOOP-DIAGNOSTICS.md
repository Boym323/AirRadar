# T5.7B event-loop and CPU attribution

The existing process-shared `runtime-health-observation` remains the only
event-loop observer. It now records bounded one-minute event-loop p95/p99/max
windows (15 windows) and resets only from its shared observer timer, so route
reads do not distort the measurement.

`runtime-performance` keeps its cumulative bounded ring and adds the same
15-minute window horizon per operation. Each operation reports wall time,
approximate process CPU time, and the residual wait time. For synchronous
operations CPU is the measured wall interval; for asynchronous operations CPU
comes from `process.cpuUsage()` and the residual is an attribution of waiting
or work outside this process. Overlapping async operations make this an
approximation, not a profiler.

The following existing hot paths are now attributable without changing their
behavior: source merge, trail update, snapshot serialization, Track Fusion,
Operational Twin, history/DB transaction, network enrichment, and SSE notify.
No payloads, stack traces, or per-request state are retained.

## Interpretation

High event-loop p99 with high `cpuMs` in `snapshot.source-merge`,
`snapshot.trail-update`, `snapshot.serialization`, or `snapshot.trackFusion`
supports synchronous CPU contention. High wall time with low `cpuMs` in
`history.persist`, `network.metadata`, or other async lanes points toward I/O or
queue wait. This is attribution evidence, not proof of a single causal line;
compare it with the matching one-minute event-loop window and CPU observer
interval.

The supplied T5.6 event-loop p99 (~1.29 s) remains a historical cumulative
result. It must not be compared directly with a new one-minute window until
the new observer has completed a common observation interval.
