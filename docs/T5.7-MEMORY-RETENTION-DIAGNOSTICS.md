# T5.7A memory-retention diagnostics

This note records the bounded diagnostic added after the T5.6 audit. It is
process-local and intentionally does not collect a V8 heap snapshot, object
graphs, retainers, payloads, coordinates, or provider errors.

## Current ownership and maximum lifetime

| Object family | Owner | Cleanup / bound | Diagnostic evidence |
| --- | --- | --- | --- |
| Local aircraft | `AircraftStateService.localAircraft` | Removed after the configured local stale threshold, subject to the existing source-affinity grace path | count, oldest `lastSeen`, stale-retained count |
| Network aircraft | `AircraftStateService.networkAircraft` | Removed after the configured network stale threshold and failover grace | count, oldest `lastSeen`, stale-retained count |
| Local trails | aircraft objects in the local map | Removed with aircraft; point count is bounded by `SERVER_LOCAL_TRAIL_MAX_POINTS` | point count, oldest point, max points/aircraft, stale-retained points |
| Network trails | aircraft objects in the network map | Removed with aircraft and bounded by configured age and point count | same attribution as local trails |
| Track Fusion Shadow | `TrackFusionShadow.tracks` | 120-second absence retention, 30-second cleanup cadence, 25,000-track cap | existing active/capacity diagnostics |
| Operational Twin outcome validators | bounded pending maps and five-minute buckets | per-validator pending cap and 24-hour bucket window; completed aggregates are compact | existing `pending`, `capacityEvictions`, and window reports |
| Metadata/enrichment | `EnrichmentService` and provider caches | bounded LRU plus positive/negative TTLs; persistent ADSBDB cache is separate and bounded | existing cache size/limit and provider hit diagnostics |
| SSE/public snapshots | `AircraftStateService.snapshotCache` and SSE coalescing | two coverage/shape cache entries, invalidated on state version change; per-connection newest-only bounded delivery | cache entry count, active clients, coalescing and payload diagnostics |
| Service auxiliary maps | `AircraftStateService` | lifecycle cleanup follows aircraft removal or history maintenance | sizes of source affinity, history, predictive, and ATC key maps |

The diagnostic is exposed only through the existing authenticated/admin system
diagnostics path as `runtime.diagnostics.retentionAttribution`. It reports
retained container membership and age, not the number of V8 bytes retained by
each object family. `staleRetained > 0` is a follow-up signal, not proof of a
leak: the source-affinity grace path can legitimately retain an observation.

## T5.6 baseline interpretation

The supplied baseline (RSS max 1691 MiB, post-major-GC heap increase 103.6 MiB,
post-major-GC RSS increase 79.2 MiB, 71,494 maximum network trail points and no
trail-limit violations) is consistent with significant live working-set and
V8 allocator retention, but does not identify a retainer. The current code audit
found bounded owners rather than an unbounded container. A production leak is
therefore not proven by these values alone.

## Follow-up measurement

Collect the diagnostic together with the existing 60-second runtime telemetry
for at least 24 hours, including a receiver restart/failure/recovery episode.
Compare `retentionAttribution` counts and oldest ages against RSS, heap-used,
post-major-GC old-space, aircraft count, SSE clients, and cache sizes. A leak
candidate is a monotonic auxiliary-map or stale-retained count after its owner
has returned to baseline, especially when it survives multiple major GCs. If
that correlation is found, reproduce in an isolated process and use an
operator-approved offline heap snapshot; no production heap profiling is part
of this change.
