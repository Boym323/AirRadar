# T5.7C – 24-hour read-only production soak

## Purpose and prerequisites

T5.7A and T5.7B introduced process-local retention attribution, 60-second
event-loop windows and per-operation CPU/wait metrics. The earlier T5.6
sampler cannot collect a 24-hour window or preserve these new metrics.
This script performs only authenticated reads. Verify that the deployed
application contains PR #700 and #701 and that its release is healthy.

WATCHLIST_ADMIN_TOKEN must already be available in a protected environment.
Never paste credentials into terminal history, PRs, logs or reports.

~~~bash
cd /var/www/airradar
T57_SECONDS=86400 T57_INTERVAL_SECONDS=60 T57_WARMUP_SECONDS=600 \
  T57_EXPECTED_COMMIT=7564d8b \
  node scripts/t57-production-soak.mjs
~~~

The optional expected-commit prefix must match the deployed application
commit; later metadata-only GitHub commits do not count as deployment.
Use a persistent operator-managed terminal or service session to prevent
an SSH disconnect from terminating the 24-hour job. Never run a build in
the live production checkout.

## Collecting and analyzing

The script uses the existing authenticated admin endpoints at
/api/system/status and /api/system/runtime-performance every 60 seconds
by default. Only the canonical HTTPS AirRadar host or loopback HTTP is
allowed. The watchlist session expires after eight hours; the sampler
renews it after six hours, and on the next tick following an unavailable read.

The output is an incremental NDJSON journal (default /tmp/airradar-t57-
followed by UTC timestamp and .ndjson) with exclusive file creation and
0600 permissions. T57_OUTPUT overrides the location. Each row is an
allowlisted aggregate without raw responses, bearer tokens, cookies,
diagnostics store IDs, PID, aircraft IDs, coordinates or SQL. Completed
60-second event-loop and hot-path windows are stored only once. Missing
polls are recorded as unavailable rather than silently dropped.

The script notices changes to PID, diagnostic-store identity and application
commit. It starts a new numeric process segment, which prevents a false
cross-process continuous conclusion. An interrupted soak still has a
readable journal. Analyze it separately as follows:

~~~bash
node scripts/t57-production-soak.mjs --analyze /tmp/airradar-t57-example.ndjson
~~~

The analyzer writes a private .summary.json and .summary.md next to the
journal, and refuses to overwrite existing summaries.

## Interpreting the report

| Verdict | Meaning |
| --- | --- |
| PASS_WITH_LIMITATIONS | At least 95% of expected samples, sufficient duration, one process and build, at least 30 steady-state samples, two distinct major GC observations, ten completed event-loop windows, and no trail bound breach |
| INSUFFICIENT_EVIDENCE | Incomplete duration, changed process, lost samples, missing major GC baselines or event-loop window evidence |
| FAIL | A reported local/network aircraft trail limit breach |

The report includes RSS, HeapUsed and Old Space percentiles, approximate
post-major-GC trends, 60-second event-loop p99/max, process CPU intervals,
object-container retention and CPU/wait attribution for hot paths. Early
vs. late decile differences are observational and cannot alone prove a
memory leak. Assess the results alongside aircraft population, cache warmup,
traffic mix and actual SSE client activity; overlapping async CPU
attribution is not an exclusive CPU profiler.

No new API, DB write, release pipeline modification, service restart,
forced GC, production inspector, heap snapshot or synthetic SSE traffic is
introduced. PR merge does NOT start the soak; an authorized operator must
launch it on the host after the release completes.
