# Codex assignment — AirRadar: direct `main`, canonical production checkout

[Česky](../cs/agents/CODEX-DIRECT-MAIN-PRODUCTION-2026-10-19.md)

**Approved by maintainer:** 19 October 2026. **Repository:** `Boym323/AirRadar`. **Production source checkout:** `/var/www/airradar`. **Public site:** https://airradar.pomykal.cz.

## Non-negotiable execution mode

- Make routine source edits only in the canonical `/var/www/airradar` Git checkout, directly on `main`. No task branches, PRs, alternate development checkouts, persistent worktrees or side directories for source development. The existing release script's transient/atomic build directories are **not** alternate source development checkouts and remain mandatory.
- This one-checkout mode is a maintainer-authorized exception to the separate-development-checkout recommendation in historical plans. All other root `AGENTS.md`, `docs/RUNTIME-INVARIANTS.md`, `docs/RELEASE.md` and deployment safety rules remain mandatory.
- Only one agent may edit/push/release at a time. Before beginning, verify the directory, `main`, `origin/main`, clean status, no pending deploy, and exact deployed identity from fresh evidence. Coordinate with any other agent. Never overwrite or reset uncommitted third-party changes.
- Work in small self-contained steps, review the complete diff, run non-destructive relevant tests, `git fetch origin main` and recheck fast-forward ancestry, then non-force commit and push straight to `main`. Never force-push, rebase published main, or bypass failed checks. If upstream moves, re-read changed files and revalidate.
- A `main` push can trigger automatic production deployment. Stop source edits in the production checkout while its release job is reading/updating it. Keep the Git tree clean for the deploy preflight. Verify that exact SHA's CI, CodeQL, release validation, deploy and public version/health before any further deploy-bearing push. If any gate fails, investigate/fix and do not claim deployment.
- Editing *tracked source* in this checkout is authorized. Changing an active Next.js `.next` build, running `npm run build`/`next build` there while live traffic is served, running dev/HMR servers, reinstalling shared runtime dependencies, writing test fixtures to the production DB, changing secrets, or restarting services manually is **not** authorized by this mode. Use CI to build/test the exact commit and the existing validated `deploy/release.sh` artifact activation with its locks and atomic `.next-release-*` staging. Do not remove those necessary transient release-build directories.
- Production DB schema changes, production configuration/secrets changes, destructive operations, manual restarts/manual releases, and any action requiring elevated system privileges beyond the established CI/CD deployment path require separate explicit approval. Do not improvise around permissions. A dirty live checkout or concurrent release is a STOP condition, not a reason to add `--allow-dirty`.

## Objective — complete the modular refactor without losing functionality

1. Capture current `origin/main`, active `/api/version`, GitHub Release, running CI/deploy, `/api/health`, sanitized diagnostics, and a baseline of file size, browser behavior, CPU/RSS/event-loop P95/P99 and SSE delivery where measurable. Never assume a previous run is still current.
2. Resolve any failing full main release gate first. Keep existing real browser validations; update assertions when a component was legitimately retired, never disable checks merely to obtain a green build. Confirm a complete deployment including working static JS/CSS, map layers before aircraft selection, and no console errors.
3. Continue the existing incremental refactor from #1087 (HUD, map layer layout, dataset parsing and map labels), #1088 (retired routes), #1086 (lean ATC), #1090 (release smoke) and #1089 (OGN and navigation focus). Do not repeat or revert already merged work. Split responsibilities in `components/airradar-app.tsx` by map lifecycle, aircraft/OGN overlay, map sources, selected-aircraft state, controls, data fetching, and presentation. Prefer focused `components/radar/` hooks and `lib/radar/` pure modules, without duplicate polling or duplicated MapLibre state owners.
4. Untangle `app/globals.css` gradually: remove proven obsolete or overridden map selectors, move feature-local styles into scoped CSS modules where practical, preserve semantic design tokens and layout/accessibility at 320/375/390/430/768/820/821/900/1024/1366/1920 px. The Layers button must be visible, clickable and open its menu with or without an aircraft selected, in both basemap/traffic drawer states.
5. Optimize only measured hotspots: avoid repeated GeoJSON serialization/source uploads, redundant ATC geometry scans, excessive DOM/React updates, duplicate label/OGN calculations and unbounded caches. Collect comparable before/after samples for CPU, RSS, event-loop stalls, map frame time and network/SSE cadence. A synthetic benchmark alone is not production proof.
6. For each removal candidate classify KEEP/DELETE/MERGE/DEFER after searching imports, dynamic refs, API routes, UI affordances, translation keys, feature registry, production diagnostics, migrations, rollback scripts, CI and external consumers. Remove only proven dead code, stale one-off scripts or safely replaced duplication. Do not delete user-facing capabilities, safety checks, public sanitized read-only diagnostics or retained native Rust/BEAST parity for a line-count target.
7. Preserve readsb -> one in-process AircraftStateService -> RAM -> bounded SSE, historical sampling into PostgreSQL, provider failure isolation, OGN independence, MapLibre semantics, auth on writes, public-safe diagnostics, full i18n and all security/runtime invariants. No microservice conversion; preserve the modular monolith.

## Test and delivery protocol for each change

- First: inspect current code and relevant tests, record baseline, update tests. Use `git diff --check`, `npm run docs:check`, `npm run features:check`, `npm run visual:check`, targeted Vitest/lint/typecheck **only where safe for a live checkout**. Tests must be synthetic/mocked/read-only; no prod DB writes and no commands that replace the active `.next` assets. Rely on CI for builds and full browser/performance gates.
- Run `node scripts/release-scope.mjs` or the documented classifier as applicable. Before push check `git status`, source diff, active deploy lock, and remote head. Commit directly to `main`, push normally, then wait for the exact SHA's mandatory CI/CodeQL/full release-browser/performance/deploy gates; do not chain deploy-bearing pushes while checks are pending.
- For a visual change, a green unit suite is not enough: verify desktop/mobile browser gates, selected/unselected aircraft, Layers menu hit-testing and static asset MIME/200 responses after restart. Treat failure as a blocker, document suspected root cause and correct in the next safe serialized iteration. Never skip test or disable guard.
- For feature/route changes update `docs/features.registry.json`, regenerate `docs/FEATURES.md`, update EN/CZ authoritative docs and regression checks.
- Each iteration report: what changed, exactly what was removed, commit SHA, test results PASS/FAIL/NOT RUN, actual observed perf delta, GitHub release/deploy result, deployed SHA and `/api/version` evidence. Do not report code merely merged in `main` as already deployed.
- Iterate autonomously through these small validated improvements until no further safe, supported changes remain or a hard blocker needs owner approval. Never claim autonomous background work outside an active Codex run.
